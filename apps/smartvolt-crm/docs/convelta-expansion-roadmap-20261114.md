## 1. 產品目標與本輪成果

Convelta 繼續主打「AI 輔助真人客服，在大量查詢中把握值得跟進的預約」。整個體驗應連成：查詢進來 → 看清需要與優先級 → 有人負責 → 適時追客 → 真實預約／到店 → 再次互動。

將既有第二輪剩餘工作與 Omnichat、SleekFlow、respond.io 的可參考能力，整理成 **六個交付批次、23 個工作包**。沿用既有工作卡，補齊未有追蹤的共用能力及新功能。批次是產品交付組合；依賴契約齊備的工作包可並行，不要求等全部渠道核准才開始開發。

本輪只新增策劃文件及跟進卡。不安裝套件、不更改功能程式／資料庫結構／權限、不部署新 App、不新增客戶或啟用任何外發。已上線的 FAQ、翻譯、分派、客戶階段、真人交接及 C 保留原有完成狀態。

保留現有收件匣、跟進、Flow、AI、知識庫及推播的工作分工；完整成效放在「跟進 → 成效」及「推播 → 活動結果」。渠道與整合留在「團隊與設定」。日常畫面只顯示當下工作與主操作，設定、來源、技術紀錄按需要展開。

| 使用者想做甚麼   | 日常操作                                                             | 系統負責處理                                                            |
| ---------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------- |

三套旅程按各自來源啟用：未回覆跟進可在已有訊息事件時使用；預約提醒及服務後回訪需要實際已確認預約／完成服務來源，沒有資料不會硬開或猜日期。

行銷發布前的必要預覽與核權，整合成一次清楚的「排程發送／啟用流程」操作，不加多層重複核准。網站掃描仍按使用者最新決定：掃完即用、見到錯就改，不恢復逐篇 FAQ 核准。

派送結果不明、撤權、需真人核對等關鍵狀態直接顯示；其他來源與執行細節收在「查看詳情」。新增表單、對話窗及畫布需有桌面／手機鍵盤、可見進度、錯誤復原、無水平溢出及可讀字體驗收。

## 5. 共用架構與資料權威

### 5.1 一套背景執行，分清用途

推播、旅程、提醒與 C 背景工作共用持久排程、限速、取消、收據及觀測；政策按用途分開：對客行銷走品牌／渠道同意與抑制，內部提醒走成員權限、裝置訂閱及個人偏好。退訂客戶行銷不會取消主管需要處理的內部工作。

現有 `sv_wa_messages`、`sv_meta_messages`、AI 請求及業務事件的證據保持原樣。新增派送工作、嘗試、回執及旅程執行帳本，透過穩定 ID 連結既有來源；逐步使用正規表、完整聚合及分頁，不一次重寫整個公司快照。

建議邏輯模型包括：聯絡偏好事件、抑制清單、受眾版本／快照、範本版本、outbox 工作／嘗試、delivery events、旅程定義／發佈版本／客戶 run／step，以及附件資產。表名與 migration 必須在實作時依現有 schema 審查後定案。

### 5.2 派送與恢復契約

- 每個工作保存 company／brand／product、用途、發起或授權者、定義版本、來源事件、受眾／收件人、到期時間與穩定 command ID。
- 工作與業務改動以交易式 outbox 記錄；持久排程器負責何時喚醒，SQL 原子 claim 與當下資格決定能否執行。
- 排隊不凍結權限與同意。每次真正發送都重查角色／產品／品牌、聯絡資格、頻率、範本及對話／預約新狀態。
- 供應商未接收前的可判定暫時錯誤可重試；網絡逾時而無法判定是否已提交，保留「待核對」，不因工作框架自動重試就重發。
- 保留 queued、dispatching、provider-accepted、delivered、read、failed、unknown、cancelled 等適用狀態及原因；各渠道不能提供的回執要顯示覆蓋範圍。
- 遲到或重複 Webhook 以 provider event／message ID 去重，不倒退已確認狀態；更正是新增事件，不改寫原始證據。
- 每租戶有併發、速率、每日上限及停用開關；小批派送／有限 fan-out，單一公司不拖垮其他公司。歷史量大時分段與獨立 run，避免無界重放。

### 5.3 渠道及 AI 模組化

以 typed `ChannelAdapter` 與明確能力矩陣處理文字、附件、原生表單、留言私訊、廣播及通話。相同 UI 按實際能力顯示操作，不把所有渠道當成可以任意群發的 WhatsApp。

網站聊天是新增 provider／channel 契約，需逐一擴充既有 provider enum、RPC、身份連結、命令驗證及收件匣讀模型；不能只加一個前端 widget，或把訪客偽裝成 Meta／WhatsApp 客戶。通話、附件及表單在時間線各有類型與來源，通話接通不等於文字訊息已讀。

AI 使用現有 AI SDK／Gateway、品牌知識與用量帳本。語音及圖像模型按當期可用能力獨立配置及評估，不能假設目前文字模型已能準確讀音檔。每個模型／工具步驟記錄來源、功能、用量及結果；AI 描述不能代替實際工具收據。

真人輔助仍是預設。可控接待逐公司開啟及限制用途；先做可核對的資料收集與有權查詢，再啟用明確允許的動作。價格、預約、收款及可用時段必須來自權威服務，資料不足時交真人。AI 分類、意向及階段更新保留為判斷及操作紀錄。

### 5.4 CRM、POS 與來源邊界

- CRM／POS 保留獨立購買、路由及角色／品牌權限。CRM-only 公司可做查詢、跟進與預約意向；POS 才能提供的數據，按其授權或已安裝外部結果來源開啟。
- CRM 是跟進及業務結果來源；已安裝 LeadHub 時，其原始 attribution snapshot 維持權威。Standalone Convelta 保存渠道提供的來源證據與 CRM 結果，不能把不明來源猜成已驗證歸因。
- 與 LeadHub／AI Creative 等 Growth OS App 的連結，依 Full Suite 或已核准跨 App entitlement 啟用；Convelta CRM／POS 沿用現行獨立購買及雙購互通契約。
- 跨 App 及外部工具使用 stable workspace／client／brand／contact／thread／source／outcome ID；姓名、電話相似不自動合併。
- 預約以實際確認事件，到店以實際記錄，實收以有權帳本減退款；支付照片、AI 高意向及「已預約」標籤不替代上述證據。
- 事件期間報表與查詢 cohort 轉化分開：明確顯示建立日、確認／到店／付款日及觀察截止。聚合涵蓋完整資料集，不以已載入的 50 人代表總體。
- 廣告帳戶、品牌及服務維度可配置。成本與歸因不完整時不計該維度 ROAS；不把整品牌支出分攤成虛構療程成本。
- Meta 回傳需先驗證當期支援事件、帳戶與權限；測試事件、平台接受與正式業務結果分層顯示。
- 原始 click ID、完整 referrer、客戶身份、訊息、交易及 provider 證據留在保護範圍，前端用 scoped RPC／摘要讀模型，不為方便 grant 原表 select。

## 7. 品質、驗收與推出方式

每個工作包各自交付完整的互動、資料、失敗復原與驗收。大功能分批發佈，基礎體驗從第一批開始維持同一設計與資料契約。

1. **契約與權限**：正反向租戶／品牌／產品／角色／撤權檢查；raw tables 保護；穩定 ID、版本、不可變來源與型別驗證。
2. **執行可靠性**：重複點擊、併發、重複或亂序事件、停止、排程改期、部署中斷、供應商失聯及結果不明都有可重現測試。
3. **UI／UX**：實際元件的桌面／手機、鍵盤、可讀性、可見進度、錯誤復原、原文／草稿保留、C 不遮擋主操作。
4. **資料與 AI**：完整聚合與樣本／cohort口徑，廣東話及中英夾雜、品牌／數字、來源不足、惡意指令與工具限制評估；不虛報提升率。
5. **正式能力**：由獲授權渠道／測試接收人及真實資料來源做有限度收發、取消、退訂、轉接及對帳；模擬成功不等於正式接通。
6. **逐租戶推出**：先於 Convelta 自家業務驗證，再在另個隔離租戶驗證配置可重用；按租戶／品牌／能力開啟，保留停止及復原路徑。
7. **證據與工作卡**：程式、schema、CI、部署、真實 provider acceptance 各自記錄。只完成規劃的卡標「規劃完成」；功能卡要有對應驗收才完成。

驗收情境最少包括：排程後退訂、排程後已約、真人接管、員工停用、同一事件到兩次、派送逾時但平台已接收、範本撤銷、客人中途改時間、訊息來自原 WhatsApp App、留言重複觸發、表單 token 竄改、圖片／收據未核實、廣告回傳重試及來源撤權。

不以沒有客人的空公司量度漏覆改善或轉化提升；先收集真實基線，再比較相同口徑與觀察期。工作量標記 M／L／XL 只表示相對複雜度，沒有日數或完成日期承諾。

- AI 回覆與真實動作各有收據；失敗不可冒稱完成，真人接管即停止不適用的自動外發。

啟用條件：`ai-budget-policy`、`real-ai-channel`；定義見 JSON `gates`。
跟進卡：`ai-controlled-replies`、`copilot-answer-quality`。
